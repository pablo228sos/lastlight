# Physics API v1: integration contract

Frozen for Abai (frontend integration) and Askar (ML / Failure Frontier) on
`feature/physics-api` for Issue #2. Schema **1.0.0**, model
**lastlight-dispatch-1.0.0**, HTTP namespace **/api/v1** remain unchanged in
Phase 02. `SimulationResult` has no new fields or silently upgraded defaults.
The Python schemas, checked-in JSON Schemas and real API fixtures are authoritative.
Every existing `SimulationResult` / `SimulationTracePoint` field in
`apps/web/src/lib/contracts.ts` is retained. Proposed additions live here; no
frontend files are changed. Both consumers use the same complete `trace`.

Base URL: **http://127.0.0.1:8000**. See [FRONTEND.md](FRONTEND.md) for complete
requests, playback, status handling and explicitly labelled offline fixture mode.

## Endpoints and first integration

| Method | Path | Result |
| --- | --- | --- |
| GET | `/health` | Model/schema versions and `status: "ok"` |
| POST | `/api/v1/simulations` | `SimulationResult` |
| POST | `/api/v1/comparisons` | Baseline and upgraded results, plus deltas |
| GET | `/docs` | Interactive OpenAPI UI (CDN assets need internet) |
| GET | `/openapi.json` | Complete, locally available machine-readable contract |

Send `{}` to simulations for the baseline: 24 kWh, SOC 0.8, minimum 0.2,
discharge efficiency 0.95, critical load 1.5 kW, no PV, 12 hours with no grid.
Noncritical demand defaults to 2 kW and is deliberately shed during outages.
It never consumes battery energy in this baseline. An empty comparison body
compares against a 36 kWh battery. `upgrade: "full_precharge"` selects SOC 1.0.

For independent development load `fixtures/baseline.result.json` or
`fixtures/comparison.result.json` directly. They are generated by the actual
FastAPI endpoints and checked against the engine, not fabricated UI numbers.
Use `fixtures/regression-16h.json` to observe all three failure events; the
12-hour comparison is right-censored for both upgrades. Every fixture retains
`synthetic` provenance. Display this as a simulated example, not a field test.

## Units, inputs, defaults

Power is **AC-side kW**, stored battery energy is **DC kWh**, time is hours,
and SOC/efficiencies are fractions in `[0, 1]`, never percentages. The complete
default input is `fixtures/baseline.request.json`. All nested objects permit
partial overrides; unknown fields, nonfinite numbers, invalid SOC order,
numeric strings and booleans passed as numbers receive HTTP 422.
Supported capacity is 0.001..20,000 kWh, each efficiency is 0.01..1,
and each power field is 0..50,000 kW. These bounds are explicit in the schemas.

`duration_hours` is 1 minute through 168 hours. `step_minutes` is an integer
1..60. A partial final interval is supported. Optional `solar.profile_kw` and
`grid.profile_online` arrays each require exactly
`ceil(duration_hours * 60 / step_minutes)` entries, including the final partial
interval. Entries are constant over their interval. Arrays override their
constant `generation_kw` / `online` settings. Missing PV data means zero PV;
no weather, coordinates or daylight is invented.

Grid power is exactly zero whenever the grid state is offline. Grid charging
is opt-in (`grid.charge_battery`), uses only spare import capacity, and stops
at maximum SOC. In an outage, battery backup requires
`inverter.islanding_capable`; PV requires **both** that flag and
`solar.islanding_capable`. Incompatible PV is curtailed and cannot charge.

## Trace and failure time semantics

Each row describes `[t_utc, t_end_utc)`. All power fields are constant over
that interval. `battery_soc` and `battery_energy_kwh` are **start-of-interval**
states; `battery_soc_end` and `battery_energy_end_kwh` are ending states.
Use `power_kw * duration_hours` to integrate energy. There is no artificial
initial/terminal row and no zero-duration row. Never assume equal row lengths:
the engine splits at both SOC boundaries, in addition to the requested step.
`solar_kw` is accepted PV, including PV used to charge; curtailed/blocked PV is
separate. `grid_kw` includes grid charging. Noncritical demand includes demand
deliberately shed by policy, and that demand counts as unserved.

Critical loads get priority over noncritical loads. `status` is
`critical_failure` if critical shortfall exceeds 1e-9 kW; otherwise `degraded`
for any noncritical shortfall (including deliberate shedding); otherwise
`normal` when grid-connected and `islanded` when offline.

`first_failure_utc` is the start of the first interval with critical shortfall.
`critical_survival_hours` is elapsed time from simulation start to that event,
including grid-connected time if present, rounded to 12 decimal hours.
Both are null if there is no failure **inside** the simulated window; null is
not infinity or a forecast. Depletion exactly at the exclusive horizon does
not count as failure. `observed_duration_hours` and `survived_full_window` make
censoring explicit. `idealized_autonomy_hours` is a separately labelled analytic
battery-only reference, and is null outside its declared assumptions. The
baseline returns **9.12 h**, at **2026-01-01T09:07:12Z**. In a 16-hour window
36 kWh gives **13.68 h**, and 24 kWh / full SOC gives **12.16 h**.

`start_utc` must carry Z or an explicit offset and is normalized to UTC. All
output timestamps end in Z and have microsecond precision at most. A fixed
2026-01-01 UTC default makes omitted timestamps reproducible. Timestamps are
rendering labels; use `duration_hours` for sub-microsecond energy integration.

## Replay, provenance and errors

The service has no cloud dependencies, random dispatch, current-time input or
run database. `input_hash` is SHA-256 of the fully resolved input, encoded as
UTF-8 JSON with sorted keys, no spaces, finite numbers and UTC timestamps.
`run_id` is UUIDv5 of `lastlight:{model_version}:{input_hash}` in the URL
namespace. The same resolved input and model version produce the same entire
response. `seed` is reserved and echoed; no random generator is used. It still
participates in input identity. `input` echoes resolved parameters for replay.
Provenance comes from the caller, defaults to synthetic, and is never inferred
from a location or relabelled as measured. Supplied provenance is a claim, not
independent verification.

Validation uses `{ "error": { "code": "validation_error", "message":
"Request validation failed", "details": [{ "location": ["body", ...],
"message": "...", "type": "..." }] } }` with HTTP 422. Raw request values
and Python exception contexts are not echoed. Internal invariant violations
return HTTP 500 with `energy_balance_error`; invalid traces are never returned.
See `fixtures/validation-error.json` and `error.schema.json`.
Unknown routes and unsupported methods use the same error envelope with
HTTP 404/405 and `code: "http_error"`; unexpected server exceptions use HTTP 500
and `code: "internal_error"`. Browser CORS preflight rejection is HTTP 400 plain
text from the CORS middleware, not a simulation JSON validation error.

`max_balance_residual_kwh` is the largest absolute per-row AC, storage or
combined balance residual; residuals, conversion losses, curtailed PV and all
source totals are returned. The model rejects absolute residuals over 1e-8 kWh.
The equations, topology assumptions and limits are detailed in `MODEL.md`.

## Generate and verify this handoff

From the repository root with development requirements installed:

```sh
python -m services.simulation.fixtures
python -m services.simulation.fixtures --check
python -m pytest tests/simulation -q
python -m uvicorn services.simulation.api:app --host 127.0.0.1 --port 8000
```

Allowed browser origins are only `http://localhost:5173`,
`http://127.0.0.1:5173` and the corresponding port 4173 preview origins.
The web owner can import a fixture or fetch the API without waiting for ML.
Other origins are not granted browser access. CORS is a browser policy, not an
authentication mechanism. Server-to-server/CLI requests do not need an Origin.

## Version freeze and variable-load proposal

The authoritative request/response pair is
`docs/physics/fixtures/baseline.request.json` and
`docs/physics/fixtures/baseline.result.json`; comparisons use
`comparison.request.json` / `comparison.result.json` in that same directory.
`regression-16h.json` contains complete named simulation results, not a request.
Every generated schema and fixture is checked by `python -m services.simulation.check`.

PR #7's schema/model 1.1.0 is an **unapproved proposal**, not this service's
contract. Accept only explicitly supported schema versions, not every string
starting with `1.`. This result's `model_version` always identifies physics;
v1 has no required `physics_version` field. ML envelopes must keep their own
model identity separate. Current v1 rejects `load.critical_profile_kw` and
`load.noncritical_profile_kw` with HTTP 422. Proposed demand profiles should
be incorporated in a separate reviewed Physics PR on the final official engine.
They would override their respective scalar loads over the existing input
intervals, share the PV/grid profile length rule, integrate actual demand for
summary totals and suppress the constant-load analytic autonomy reference.
The event split inside an interval must continue to use that interval's demand.

Adopting profiles changes the accepted input, resolved input echo, input hashes
and run IDs even for scalar requests if null profile defaults are added. It
requires an explicit schema/model version update, regenerated JSON Schemas,
OpenAPI and full fixtures, updated proposed TypeScript fields, and review by
both consumers. Preserve all current result fields and the exact-horizon fix.
Until that review, consume one frozen v1 contract. See [RELEASE.md](RELEASE.md)
for the compatibility findings and coordination status.
